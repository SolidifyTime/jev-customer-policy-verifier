## 1. 项目目标与交付

给定业务规则、对话历史以及一条待审核的客服回复，训练小模型判断该回复是否符合规则。

每条模型输入包含三部分：

1. `policy`：当前样本提供的业务规则。
2. `conversation`：截至当前时刻的客服对话与已发生的动作观测。
3. `candidate_response`：单独列出的待审核客服回复。

输出为“符合规则 / 违反规则”的选择及两个候选项的概率。应用场景是在客服发送回复前，检查错误承诺、条件遗漏、例外处理和规则适用等问题。

采用的训练数据方案是：**原始训练样本＋先提取场景事实再生成的变体**。

项目重点是实现可追溯的场景提取、受事实约束的数据生成、必要的质量检查和小模型训练，交付：

- 有明确划分、来源与质量记录的训练数据。
- 可以批量运行的数据构建流程与复现说明。
- 一个能进行客服回复合规判断的小模型。
- 在固定验证集、最终测试集上的性能与错误分析报告。

当前仅安排这一条训练路线。报告数据构建过程、质量和最终模型表现，结论限于实际实验支持的范围。

## 2. 数据来源与任务定义

2026-10-02 已完整拉取作者 Task 2 目录全部 9 个 JSON：英文 `f1`、`f2`、`f3` 及阿拉伯语、德语、西班牙语、法语、印地语、中文 `f1`。这些文件是同一底层集合的语言与规则格式版本；本项目使用完整 `test_task2_en_f1.json`，统一用英文生成及评测，其他版本归档但不重复计入独立训练源。文件哈希和对齐结果已固定在 `data/source/task2/manifest.json`。

本地已核对英文 f1 文件的字段与数量：文件包含 1,982 条配对记录，分别提供原始合规回复和改写的违规回复，可展开为 3,964 个候选样本；共有 498 个 `orig_conv_id`。仍需进一步审计标签质量、来源关联和异常记录。源文件哈希及初步核查结果见[本地小试运行说明](../reports/local-pilot.md)。

论文的直接判断方法使用相关规则片段、对话和待审核回复。训练与评测保留所选文件实际提供的规则及输入条件，不能擅自补充测试样本没有提供的信息。

### 2.2 规则与标签的来源

训练材料直接使用 TOD-ProcBench 训练分区中每条样本自带的规则、对话、回复与原标签。一次生成请求只传入该样本的相关规则，不需要读取整份业务规则库。

规则中的条件、例外和逻辑关系必须保留。场景提取可以把规则整理为结构化约束，但最终训练样本仍保留原始规则文本，并保存提取内容与原文的对应关系。

ABCD 是 TOD-ProcBench 的上游来源，可用于追溯原始对话及核查关联。本项目的数据划分以选定的 TOD-ProcBench 版本为准。

原标签作为构建变体时的预期答案，不保证变体自动继承正确性。模型生成、抽取和原始标注均可能出错，需要核验。该数据结合人工场景对话与合成回复，不等同于真实商家的生产客服日志。

## 3. 先划分，再提取和生成

### 3.1 分区用途

按原始对话分组，暂定训练、验证、最终测试约为 **60% / 20% / 20%**。比例是实施起点；整组划分优先于精确的样本行数或类别比例。

| 分区 | 使用方式 |
| --- | --- |
| 训练部分 | 原始样本直接参与训练；允许提取场景、生成变体并合并训练 |
| 验证部分 | 保留原始样本与参考标签，用于检查训练过程、选择模型和阈值 |
| 最终测试部分 | 保留原始样本与参考标签，配置确定后用于最终评测 |

只有训练部分进入场景提取与生成 API。验证和测试样本不用于制作训练变体，最终测试不参与提示词与模型选择。

### 3.2 如何避免关联样本跨区

3,964 条记录不是 3,964 个互不相关的场景。划分前需要核查原始对话 ID、正反例配对关系及公开来源映射。

同一原始对话的不同截取位置、合规与违规回复、语言或格式变体必须留在同一分区。不能只按正反例配对编号分组，而忽略它们是否还属于同一段更长对话。

保存来源文件版本或哈希、分组依据、随机种子、每组所属分区和各区标签统计。进行跨区重复与近重复检查。

已按所选公开文件的 `orig_conv_id` 完成分组，同一 ID 的所有片段与正反例继承相同分区。英文规则格式按除规则文本外的内容对应，多语言文件按原始 ID、行顺序和历史长度对齐；翻译语义未逐条审核，当前不混入额外训练材料。

所有合成后代继承其训练源样本的分区和原始对话组编号。

### 3.3 评测结果如何表述

最终成绩应标注为 **“TOD-ProcBench Task 2 自定义划分上的测试结果”**，并公开划分方法与范围。

它评估对保留的未见对话的表现。共享业务规则、数据来源和构建体系的情况下，不能自动视为对新公司规则、新行业或真实生产流量的泛化证明。自定义划分的成绩也不直接等同于论文在完整测试集上的成绩。

## 4. 数据构建流程

```text
核查指定版本的 TOD-ProcBench Task 2
  → 按原始对话分组，固定训练 / 验证 / 最终测试
  → 读取训练部分的原始规则、对话、待审核回复和标签
  → API 提取带来源依据的场景事实与判断条件
  → 检查提取结果，排除信息不足或存在冲突的材料
  → API 根据结构化内容生成对话及待审核回复的变体
  → 程序检查格式、原文依据及可机械核对的约束
  → 精确去重，默认抽查 3 条并记录结论；移除抽查发现的问题样本
  → 导出实验变体，区分已抽查与未逐条复核状态
  → 原始训练样本＋合成变体
  → 训练小模型，使用原始验证和测试样本评测
```

首版先控制合成数据规模，后续每批默认仅抽查 3 条，可用参数减至 2 条。模型自动审核默认关闭；现有逐条复核结果作为历史质量记录保留。操作入口见[少量抽查与导出说明](../guides/spot-check-guide.md)。

可以使用 OpenRouter 调用文本生成模型。具体模型、费用及输出用于训练数据的条件在实施时核查并固定。各阶段调用次数与批量大小根据首批质量和成本决定。

### 4.1 提取什么场景信息

把一条带标签的训练样本整理成以下内容，并为关键事实保留原始发言或规则位置作为依据：

| 提取项 | 来源与要求 |
| --- | --- |
| 适用规则及逻辑关系 | 来自原样本规则，保留必要条件、替代条件、例外和适用范围 |
| 客户诉求 | 来自对话，说明客户希望解决的问题 |
| 已知事实 | 仅来自截至当前的对话或已发生的动作观测，每项附来源 |
| 未确认信息 | 明确记为未知，区分“没有提到”和“明确不存在” |
| 对话进度 | 哪些信息已询问或确认、哪些动作已发生、尚缺什么 |
| 待审核回复的主张 | 单独记录该回复承诺、拒绝、询问或声称的内容 |
| 预期标签与依据 | 记录原标签，并说明它与规则及事实的关系；无法解释时跳过扩写 |

待审核回复可能故意违反规则，其中的陈述不能被提取为客户事实。不能从标签反推或补造支持它的对话内容。

若多条训练样本确实共享相同规则和历史，可以复用公共事实提取结果；各自回复的主张、标签与依据仍需分开保存。

### 4.2 如何检查提取结果

先进行字段、引用位置和必需项等程序检查，再在少量抽查中对照规则、原始材料和新样本，关注会影响标签的事实与逻辑错误。

当前提取提示词在输入中提供 `policy_quote_options`，要求规则引用逐条复制短原文，并把规则解释、历史事实、未知状态和待审核回复主张分开。原标签作为待核查标注，不强制生成支持它的解释；5 条定向复测结果及剩余问题见[提示词调整记录](extraction-prompt-update.md)。

重点检查：

- 提取的事实能否在原对话中找到依据。
- 是否遗漏会改变判断的条件或例外。
- 是否把未知信息改成已确认事实。
- 是否混入待审核回复中的错误主张或未来信息。
- 原标签是否能由实际规则、对话和回复支持。

存在冲突或歧义时先跳过该源样本的扩写并记录原因。对疑似有误的原始训练标签单独核查、保留处理记录，不静默改标签。数据清理决定仅基于训练材料。

### 4.3 根据场景生成变体

生成模型接收原始规则、核验后的场景事实、对话进度、回复主张和预期类别，生成新的对话表达及单独的待审核客服回复。

首版允许改变措辞、语气、句式，以及不影响判断的姓名或标识符。标识符变化需前后一致。决定答案的业务事实、规则、条件关系、信息披露顺序和回复核心主张保持不变。

保留未知状态：不能为了让对话更自然而擅自补齐收据、会员、订单或确认状态等信息。原样本如果包含影响判断的动作观测，也应保留相应信息与先后关系。

当前生成提示词明确保留原发言的条件关系、未知程度、动作对象及同一违规点，并要求同时改写历史和回复。仅仅保持标签相同仍可能改变原例含义；两轮定向复测的结果与剩余问题见[生成提示词复测](generation-prompt-update.md)。

每个生成样本仍包含规则、对话历史和独立待审核回复；答案及生成解释单独保存。语言与输入格式跟随所选数据版本，具体生成提示词在核查真实字段与样本后制定。

一份通过检查的场景结构可以复用，多次调用生成模型，得到同一源样本的多个候选变体；不必每次重新提取。每次都围绕原有标签和回复主张生成，不能把前一次变体中新增或错误的事实当成新的来源依据。对多个结果去重并少量抽查，统计来源、标签分布和程序通过率，避免少数容易生成的场景或某类标签占据大量样本。

### 4.4 检查变体与标签

程序验证字段、来源引用、格式、对话是否变化和精确重复等；再按固定种子抽取少量变体，优先覆盖两类标签和不同源场景。抽查只填写“通过／剔除／待定”，有问题时写一句备注。

抽查重点是新样本自身的预期标签是否成立，以及是否新增会影响判断的事实。普通措辞、语气或不改变标签的改写差异可以通过，不再以完全等义为验收条件。被剔除或暂缓的条目不进入本次实验文件；其余条目保留各自的已抽查或未逐条复核状态。少量抽查不代表整批质量认证，未抽中项可能仍有噪声或近重复。

首批试验中的两次模型审核调用保留为对照记录，后续默认跳过。抽查发现个别问题时不自动扩大人工检查量；保留问题记录，通过固定划分上的训练与评测判断合成数据的实际作用。

### 4.5 小批量复核与数据统计

首批已选择 50 条训练源样本，兼顾两种标签并覆盖不同原始对话和业务类型；首轮每条最多生成 1 个变体，22 份场景提取通过检查，按当时程序检查有 12 个变体进入待复核。**12 是首次生成的阶段结果，不是 50 条源样本最终可生成的样本数。**复用 22 份场景各追加生成两次后，新得到 20 条通过当前程序检查的候选；新增的空白变化检查也将首轮候选从 12 条修正为 11 条，合计 31 条。首批采用完整人工复核以识别主要问题，后续改用少量抽查。

按源样本、业务类型和标签统计提取通过率、程序通过率、重复率、抽查发现的错误及每条保留样本的 API 成本。先完成固定划分上的原始数据基线训练，再加入合成数据做同条件对比。不把少量候选的存在写成数据增强带来的性能提升。

本轮 31 条候选已完成最终复核：通过 15 条、拒绝 12 条、待定 4 条。通过项全部来自训练分区，保留原文、来源和复核依据；源行 1028 的违规回复与 1177 的合规回复另列为原始数据基线的标签排除项，未直接改标签，也未扩展到未复核的配对回复。

## 5. 数据记录与防止泄漏

实际字段名须与公开文件核对。项目内部至少保存以下信息：

| 信息类别 | 内容 |
| --- | --- |
| 模型输入 | 规则、对话历史、待审核回复 |
| 训练目标 | 合规二分类标签 |
| 数据来源 | 原始文件与版本、源样本 ID、原始对话组、配对关系、分区 |
| 样本关系 | 原始或合成标记、父样本 ID、变体编号 |
| 场景提取 | 事实、未知信息、规则条件、回复主张、原文依据 |
| 质量记录 | 程序检查结论、失败原因、抽查状态、抽查者及依据 |
| 复现信息 | 模型、参数、提示词版本、调用用量与费用 |

标签、场景提取中的判定理由、违规类型及带答案含义的编号不进入模型输入。原始样本和变体使用一致的输入格式，来源标记用于管理与统计。

在任何生成调用之前冻结分区。仅训练部分可用于场景提取和合成；验证部分用于训练调试，最终测试保留到配置确定后。所有合成样本继承其父样本的训练分区。

语言翻译、格式改写、同一对话的其他片段和正反例均属于关联材料，不能跨区使用。

## 6. 模型与训练

**训练路线已变更为 SemIf-OpenJev Direct，以下实现以当前指南为准。** 加载完整预训练 `Qwen/Qwen3-0.6B` Transformer 和原生共享词嵌入的词表头，保持原模型结构。一条 chat prompt 包含业务证据、criterion 和 A/B 选项，不解码文本；从最后位置的原生词表 logits 读取 A/B 概率，使用二项交叉熵、统一学习率进行全参数监督训练。上游提供推理参考，监督训练由本项目实现。此前随机候选头、独立路径和 CE＋Brier 路线已归档，见[历史指南](../archive/agentjev-training-v1.md)。

当前 Direct 协议为 `customer-policy-semif-direct-v1`，通过 LLaMA-Factory 自定义 Trainer 进行全参数监督训练。AutoDL 用 PyTorch 2.5.1 / CUDA 12.4 基础镜像开机，实际目标为 RTX 4090 / Ubuntu 22.04 / Python 3.12 / PyTorch 2.6.0 + cu124，步骤见[训练说明](../guides/jev-training.md)与[接入设计](llamafactory-training.md)。当前 2.6.0 本机 CPU 的 108 项测试、三轮样本覆盖、跨轮续训、TensorBoard 写入、所选模型重载与导出通过；正式训练默认 3 个 epoch，完整 Qwen3-0.6B GPU 训练尚未启动。
