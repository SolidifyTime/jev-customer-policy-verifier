## 审核顺序

先审核一个源场景的规则、原始对话、原始待审核回复和提取结构，再审核它下面的各个变体。`compliant` 是符合规则，`violating` 是违反规则；它们都是预期标签，需要你判断是否成立。

1. **源标签是否有依据？**只依据给定规则和截至当前的对话，判断原待审核回复在这一刻是否合规。正确的中间步骤可以是合规回复，不要求一条回复完成整个流程。源标签明显不成立可拒绝整个场景；解释不清楚时标为待定，并暂缓下面的变体。
2. **提取是否准确？**核对提取中的规则和事实引用、已知与未知状态、对话进度及回复主张。提取内容也是模型产物，不能当作标准答案。若发现重要错误，在源场景依据栏写明，不直接修改原始材料。
3. **变体是否保留原义？**对比原始与变体对话、待审核回复，检查关键条件、事实、动作顺序和核心主张是否一致。
4. **新回复的实际标签是什么？**根据新样本本身判断符合、违反或无法确定，再与预期标签比较。两条回复都合规也不代表保留了同样的主张；两条都违规也要检查是否保留了同一个违规点。
5. **是否有实际改写？**仅改空格或几乎复制原文不应当作有效新增。回复没改而对话有实质改写，并非必然拒绝，但需要记录新增信息量较低；同源变体之间也要避免过度重复。

主要关注会改变业务判断的差异。普通拼写、礼貌程度和句式变化不需要苛求，只要含义清楚且未改变事实或回复主张即可。

## 特别容易出错的地方

| 检查项 | 审核时的注意点 |
| --- | --- |
| 事实与回复的边界 | “待审核回复”尚未发送，里面的陈述不能作为过去已经发生的事实。违规回复故意包含错误主张时，要保留该错误，而不是帮它纠正 |
| 未知状态 | 客户给了身份资料不等于已经核验身份；没提发货、会员级别、退款结果时，不能默认已确认 |
| 条件和例外 | 区分“且／或”、必须／可选、如果／除非；核对会员等级、金额、天数和订单状态 |
| 动作与顺序 | 请求资料、承诺查询、实际完成查询是不同动作；不能提前完成原样本尚未发生的步骤 |
| 回复主张 | 询问、拒绝、承诺、提供建议不能任意替换；没有依据的新优惠、新拒绝或新操作都可能改变判断 |
| 判断范围 | 按样本给定规则判断当前回复，不补充自己熟悉的商家常规，也不要求已经完成所有后续步骤 |

已知重点案例：源行 481 曾将“全名、账号 ID **和**订单 ID”改成“全名**或**账号 ID，再加订单 ID”；1476 涉及“提供资料是否等于核验完成”和运输状态的含义；1403 曾额外增加不能给折扣的主张；1028、1706、599 的源标签或当前动作存在疑问。这些是当时的助手初查提示；最终判断以已填写的复核报告为准。

## 怎么填写结论

每个源场景填写“源标签有依据”“场景提取准确”“源场景结论”和一句依据。每个变体填写“保留性”“新回复实际标签”“最终结论”和一句依据。将“待填写”替换为所选结论即可，不需要修改对话或润色英文。

| 最终结论 | 使用条件 |
| --- | --- |
| 通过 | 源场景可解释，提取无关键错误；变体保留事实、条件及主张，实际标签与预期一致，有实际改写 |
| 拒绝 | 明确发生事实或主张漂移、标签翻转、重复，或源材料明确不成立；写明拒绝原因 |
| 待定 | 规则、来源事实或标签解释不足，暂时无法判断；写明疑问，后续单独处理 |

依据尽量写成“规则要求什么 → 对话已知什么 → 回复做了什么”。例如：“规则需先问会员级别，原回复跳过该步骤询问日期；变体改问会员级别，改变了违规点，拒绝。”

填写示例：

```text
保留性：否
新回复实际标签：符合
最终结论：拒绝
依据：原回复要求姓名、账号 ID 和订单 ID，变体把前两项改成二选一，改变了回复的条件关系。
```

审核结束后由我们汇总通过、拒绝、待定数量并导出训练候选；待定项不进入训练。统一文件包含源数据，因此放在 Git 忽略的运行目录里。生成脚本会拒绝覆盖已有复核文件，避免丢失你填写的结论。
